# Apartment-only edit latency: trace and safe follow-up

## Scope / evidence

Read-only trace of the existing Swift client, bridge mutation path and PM3 adapter, cross-checked against `/tmp/rides-ui-physical-bridge.log` (the prior physical bridge run, Nov 18, 2026). No live calls or device writes were made for this investigation. The log contains no per-request wall-clock timestamps, so it is cited by line sequence / endpoint order and its recorded durations, not by invented clock times. It contains no hardware block values or credentials in this report.

The app has two distinct scans relevant to apartment editing:

* When an apartment secret is first set while a token is loaded, `RidesViewModel.apartmentSecretDidChange` can trigger `refreshForApartmentSecret`. This performs an apartment-capable scan (`GET /api/v1/hardware/page0/scan`, then `GET /api/v1/hardware/page0/missing` to get block 3) before enabling the feature. It checks 4/5/6 against the loaded token before retaining pending rides.
* A subsequent apartment-only save (with the snapshot already ready) does **not** do that preliminary scan. It encodes block 4 locally and sends one conditional mutation POST. If Auto scanning was running, it drains its in-flight scan before the write and does one post-write confirmation scan before resuming. If Auto was not running, that particular refresh is not requested.

The physical log records two successful **2-target** mutation requests (around lines 144–164 and 1994–2010). One took 2,957 ms total (session-open 476 ms, preflight 848 ms, write/verify 1,631 ms); the other took 2,946 ms (session-open 467 ms, preflight 848 ms, write/verify 1,630 ms). Full page0 scans immediately followed, taking 1,899 ms and 1,901 ms respectively. These are historical examples only: the log records target and write counts/timings but does not log mutation block identities or request payloads, so the 2-target requests cannot be identified as apartment-only edits. Two targets do not imply two writes: the apartment-only block-3 compare guard is a no-op and normally leaves one actual write (block 4), whereas a 2-target ride-mirror operation can write both blocks 5 and 6. Consequently, the log provides **no verified apartment-only mutation timing**, and these 2-target durations must not be presented as an apartment-edit measurement. They are not a new benchmark or a breakdown of individual native commands. Any user-perceived total additionally includes iPad-side latency, scheduling, and possibly a scan drain / refresh.

## Exact apartment-only request and guard sequence

1. `saveApartmentEntry` passes the loaded token, exact in-memory secret and validated apartment number to `performApartmentWrite`. For apartment-only edit `includeCharge` is false. Swift computes the encoded apartment block locally.
2. `NetworkRideTokenDevice.writeApartment` builds one `POST /api/v1/hardware/page0/mutations` for two targets, ordered by the bridge: block 3 with expected=current block 3 and desired=same block 3; block 4 with expected=current token block 4 and desired=new encoded apartment block 4. No block 5/6 targets are included for an apartment-only operation. The response must verify both target values.
3. `Page0MutationValidator` permits only page-0 blocks 1–6, normalized 32-bit hex, unique targets, and a supported API version.
4. `Page0ConditionalWriter` opens a serialized, request-scoped optimized mutation session. The PM3 adapter ensures connection, invalidates cached T55 detect state and freshly runs `EnsureT55SessionActiveAsync` (native `T55DetectCommand`). It holds the operation lock until session disposal.
5. The bridge freshly reads **each target once**, in block order (3 then 4), before any write. For each, actual must equal either request expected or request desired. Any other value is a conflict and prevents all writes. If all are already desired, it returns already-applied without writes. This includes the expected=desired block-3 no-op guard: current block 3 must still equal the snapshot's block 3, then no write to block 3 is issued.
6. For each remaining target currently at expected, the adapter issues `T55WriteBlockCommand`. The native PM3 write service performs read-back verification as part of its successful write result; this optimized path returns that verified result without a second explicit read command. A compatibility mutation-session implementation instead writes and then explicitly reads back. Bridge checks verified actual equals desired.
7. On write/verification failure after a write attempt, bridge attempts reverse-order restoration to each expected value with a bounded recovery token and verifies each restoration. The mobile caller treats ambiguous transport failure as refresh-required, never a blind retry. On success, the app adopts the mutation response as its local result. If Auto had been paused for this operation, `refreshAfterMutation` subsequently issues a full page0 scan to re-confirm current token state, then Auto resumes.

## What's redundant, and what's safety-critical

* **Redundant with the optimized native write path:** a separate explicit post-write block read for a write already reported verified by the native PM3 service would duplicate read-back. That duplicate is already avoided by `WriteDetectedPage0BlockVerifiedAsync`; do not add another verification read. The historical aggregate write/verify timings above cannot be attributed to apartment edits or split into write and native-verification costs.
* **Not a second no-op write:** block 3 is an intentional compare-only guard. The bridge reads block 3 during preflight and sends no write if it matches. Removing it would lose the stale-token check binding block 4's apartment encoding to the block-3 key context.
* **Necessary:** serialize the mutation, force fresh detect, preflight all expected values before the first write, refuse third-party/stale values, verify successful write results, recover after partial/ambiguous writes, and surface ambiguous failure for operator refresh. Block 4's expected-value guard prevents overwriting an apartment changed since the app snapshot.
* **Potentially redundant at the UI level:** the post-mutation full scan is specifically tied to pausing active Auto scanning and serves as a broader re-confirmation after the protected mutation. Do not remove or narrow it without proving what state/identity guarantees Auto requires. If Auto was not active, the path already trusts the exact response values and does not unconditionally rescan. Also, fresh secret-configuration snapshot and post-write Auto refresh serve different purposes and should not be conflated.

## Future optimization candidate (decision only)

First add per-operation client-side timing/correlation around secret-triggered snapshot, mutation POST, Auto drain, and post-write refresh, and PM3 per-command timings (detect, each preflight read, write including native verify). Current bridge logs isolate session-open, aggregate preflight, aggregate write/verify and endpoint total, but cannot identify the dominant native operation precisely.

If those measurements confirm the dominant cost is multiple serial PM3 round trips, a future native PM3 batch may combine **read-only** preflight reads (block 3 and 4) under the same exclusive, freshly detected session, and/or expose detailed phase timings. Keep all expected-versus-desired guards and no-op behavior unchanged. Batching writes is not recommended without verifying that the native API preserves per-write readback and the existing partial-write recovery contract. Do not skip fresh detect, preflight, compare-only block 3, verification, rollback, or required Auto refresh solely to improve latency. No optimization is justified by the present aggregate timings alone.
